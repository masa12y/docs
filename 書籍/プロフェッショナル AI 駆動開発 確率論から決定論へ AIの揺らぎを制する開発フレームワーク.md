# プロフェッショナル AI 駆動開発 ― 要約
### 確率論から決定論へ：AIの揺らぎを制する開発フレームワーク

> 原著：松本淳太郎（サカモト）著／株式会社松尾研究所 金剛洙 監修（技術評論社）

---

## 全体像・基本思想

AIコーディングは既に開発現場の主流になったが、多くの現場は「バイブコーディング」（AIの出力を検証せずに受け入れる開発スタイル）の代償に苦しんでいる。この問題を「運」や「腕」の問題ではなく、**LLMという確率マシンの性質を理解した上での工学的な制御問題**として捉え直す。

中核となるのが **Y = F（X）** というシンプルな式である。

- **X（インプット）**：AIに与えるコンテキスト（プロンプト・ルール・コードベース・ドキュメント・スキル・外部情報・対話履歴）
- **F（変換）**：LLMそのもの。確率的にXをYへ変換する「癖のある確率マシン」
- **Y（アウトプット）**：AIが生成するコード。テストという合格基準で判定される

この3変数を**X→Y→Fの優先順位**で独立に制御し、さらに X・Y・F を横断する「AIによる相互レビュー」で品質を面的に守ることで、AIの出力を「祈って待つもの」から「設計して走らせるもの」に変える。

## 第1章 AI駆動開発の現状と課題

### バイブコーディングの代償
AI利用は爆発的に増えているが、AI出力への信頼度はむしろ低下している（Stack Overflow調査：不信率31%→46%）。バイブコーディング（検証なき信頼）の代償は3段階で現れる。

1. **本番事故**：ReplitのAIエージェントが本番DBを削除するなど、検証を挟まない体制では「立ち止まる」機構が存在せず事故が必然化する。
2. **誰も理解していないコードの蓄積**：AI生成コードは急増する一方、リファクタリングの比率は低下し、脆弱性を認識したまま出荷される割合も高い。
3. **書く時間の減少と確認時間の増大**：AIで「書く」速度は上がっても「確かめる」速度は変わらず、体感の生産性向上（1.5〜2倍）は頭打ちになる。

### なぜ失敗は必然なのか（LLMの2つの癖）
1. **出力の揺れ**：同じ指示でも毎回異なるコードが返る。人間コードと比較し、ロジックエラー1.75倍、パフォーマンス非効率8倍などの問題頻度が報告されている。
2. **単一ゴールへの近視眼的最適化**：AIは「指示された機能を動かす」ことにのみ最適化し、可読性・保守性・SSoT（Single Source of Truth：1つの事実の情報源は1箇所という原則）など明示されていないゴールを取りこぼす。

### 認識されない技術的負債
手動開発では「妥協した」という違和感が負債の検知装置として働くが、AI駆動開発ではこの検知装置が消える。妥協は記録されず、歪んだコードがそのまま次のAI生成の手本（コンテキスト）として再投入され、負債は「無謀かつ無自覚」の象限（Fowlerの技術的負債4象限）に集中し、加速度的に膨張する。この悪循環がたどる典型的な経過が「**3ヶ月の崖**」である（1ヶ月目は新機能開発が9割、3ヶ月目にはデバッグ・動作確認が9割を占めるようになる）。

### なぜ進行中に気づけないのか
METRの実験では、AIツール利用で実測19%作業時間が伸びたにもかかわらず、開発者自身は20%速くなったと感じていた。これは「速度の錯覚」「自動化バイアス」「ダニング=クルーガー効果」という3層の認知バイアスによるもので、**感覚はAI駆動開発の計器にならない**。測れる仕組みを外部に置く必要がある。

### バイブコーディングが通用する境界
個人開発・POC（試作）では有効だが、企業のPOCの88%は本番展開に至らない。境界を分けるのは技術力ではなく「失敗のコスト」である。本質は、本番で使われ続けるソフトウェアをAIの速度を捨てずに作る方法を確立することにある。

## 第2章 AI駆動開発のフレームワーク：Y=F（X）

### 3変数の定義と放置した姿
- **X（インプット）**：AIから見える世界のすべて。放置すると「不足」「分裂」「鮮度切れ」の3形態で劣化する。
- **F（LLM）**：癖のある確率マシン。放置とは「揺れを消す」ことではなく「揺れを前提とした設計」を欠くこと。
- **Y（アウトプット）**：合格基準（テスト）を事前定義せずに人間の目視だけに頼ると、「目視合格の錯覚」「フィードバック係への転落」「判定の飽和」が起きる。

### 好循環と悪循環（フィードバックループ）
生成されたYはリポジトリに蓄積し、次のタスクのXの一部になる。**汚いYの再投入は悪循環を、きれいなYの蓄積は好循環を生む**。シミュレーションでは、リファクタリングをしないプロジェクトの実装完了確率（AIが1回の試行で要求を満たす確率）は90%から50回で40%まで一直線に低下する一方、10回ごとにリファクタリングするプロジェクトは85〜90%を維持し続け、累積成功数は1.3倍の差になる。

法人向けファイル共有サービスの物語（結末1：ルールもテストもなくSSoTが崩壊し情報漏洩に至る／結末2：ルールとテストがあり分裂を検知・修正して主力製品に成長する）を通じて、同じ1週間のバイブコーディングから出発しても、循環の向きひとつで結末が真逆になることを示す。

### どこから制御するのか：X→Y→Fの優先順位
1. **Xを最初に整える**：今日から整備でき、書いた分だけ即座に効く。Fの材料そのものであるため上流に位置する。
2. **次にYを固める**：Fの出力の合格範囲を定義する。
3. **最後にFを整える**：モデル自体は各社が進化させるため、開発者が設計するのは「選び方と使い方（オーケストレーション）」のみでよい。

この順序（X→Y→F）に従い、入力コンテキストの設計、テストによる自動判定、モデル編成、横断的レビュー、実践フロー、組織展開へと段階的に品質管理を積み上げる。

## 第3章 インプット制御のためのコンテキストエンジニアリング

### 原理
AIの挙動は「そのとき与えられている情報（X）」だけで決まる（AIが一度に見られる情報の置き場を**コンテキストウィンドウ**と呼ぶ）。AIエージェント時代のXは、開発者が書くプロンプトだけでなく、AI自身がファイル読み取り・検索・コマンド実行によって組み立てるものになった（＝コンテキストエンジニアリング）。この「何を読みにいくか」というXの組み立てを支えるのが、AIコーディングツールの実行基盤である**ハーネス**であり、ハーネスが持つ接続手段の範囲がAIの世界の広さを決める（接続されていない情報はAIにとって存在しない）。良いXの条件は「量」ではなく「情報効率」であり、**短く・具体的で正確・整合していること**が求められる（Chromaの Context Rot 研究：入力が長くなるほど回答品質が連続的に低下し、Lost in the Middle により中央部の情報は見落とされやすい）。

### コンテキストの7要素
1. **プロンプト**：唯一その場で手で書く要素
2. **ルール**（CLAUDE.md / AGENTS.mdなど）：セッション開始時に自動で読み込まれる「プロジェクトの憲法」
3. **コードベース**：既存コードそのもの。量が最大の「暗黙の教師」
4. **ドキュメント**：仕様書・設計書など
5. **スキル**：特定タスクにだけ効く手順書・ノウハウ
6. **外部情報**：DB実データ、エラーログ、CLIやMCP経由で届くリポジトリ外の事実
7. **対話履歴**：セッション中の記憶。最も劣化が速い

### コンテキスト品質の3原則
1. **鮮度（Freshness）**：常に最新の事実と一致していること。違反の典型が「タイムカプセル仕様書」（書かれた瞬間から現実と乖離していく文書）。
2. **必要十分性（Sufficiency）**：過不足なく与えること。不足は暗黙ルールの未明文化、過多は前タスクの情報の持ち越しに現れる。
3. **一貫性（Consistency）**：情報どうしが矛盾しないこと。違反の典型が「二枚舌ルール」（ルールファイルと実態、あるいはルール間の食い違い）。解決策はSSoT（正本を1箇所に置く）。

### 3原則を守る対策
- **実行前の対策**（6要素を静的に整備）
  - **ルール**：簡潔に保つ、機械的に従える具体性で書く、単一情報源を1箇所に置く（食い違いに気づいたら先送りせずその場で正す）。
  - **コードベース**：鮮度＝使われていないコード（コメントアウトの残骸・呼ばれない関数）を残さない。必要十分性＝2つのアンチパターン「**散在したコード**」（関連処理が複数フォルダに分散し探索コストが増える）と「**ゴッドファイル**」（1ファイルに多責務が詰め込まれ無関係な情報までXに載る）を避け、1ファイル1責務とフォルダ直下の**索引README**（1行説明で目次化する）で探索を短くする。一貫性＝SSoTを保つ設計に集約する。
  - **ドキュメント**：実装のPRと同時に仕様書を更新する／維持できない文書はXから外しコードを唯一の真実にする、の2段構え。局所的な決定は**コードコメント**にその場で残し、横断的・大きな意思決定は**ADR（Architecture Decision Record）** という形式の独立文書に記録する。ADRは決定を1件1レコードで残し、決定が覆っても古いレコードは書き換えず「Superseded（置き換え済み）」の印と新決定へのリンクを添えて積み上げる（棄却した案を後から再提案してしまう手戻りを防ぐ）。
  - **スキル**：同じ手順を繰り返しチャットに貼っている／ルールの一節が手順に育ってしまった、が切り出しの合図。外部接続の取扱説明書（CLIの使い方、困ったときに見る場所）を書く用途によく使われる。
  - **外部情報**：接続する価値のある代表例として、ログ基盤（Sentry等）、データベース、タスク管理ツール（Notion/Linear等）、GitHub（レビュー指摘の傾向）、Web調査（最新ドキュメント）、プロジェクト固有の情報源（Google Sheets、Stripe CLI等）を挙げる。CLIは「結果を取り込む経路」、MCPは「外部サービスを参照先として接続する経路」という役割分担。ただし接続はタダではなく、ツール定義文が常時Xを占有するため、必要十下つなぎ使わない接続は外す。
  - **対話履歴**：唯一「書いて整える」ものがなく、実践は「捨て方」。①タスクの意味的な区切りで新セッションを始める、②ウィンドウが溢れそうならハーネスのコンパクト機能（要約圧縮）で畳むが、これは撤回した方針を有効な指示として誤って残すことがあるため応急処置に留める。誤った前提が履歴に自己強化されていく例として、Google Gemini 2.5のテクニカルレポートが報告するゲームプレイ検証中の事例が挙げられている。
  - **サブエージェント**（コンテキスト分割の道具）：「結論だけあればよい」調査系の仕事を別コンテキストの子AIに任せ、本体は結論だけを受け取る。例：複数ライブラリの比較調査、ログ・DB・コードを突き合わせたバグの原因候補の列挙。Fan-out（独立並列）・Pipeline（逐次）・Specialist（専門家）の3パターンに整理される。ただし分割はタダではなく、各サブエージェントが自分でコンテキストを掴み直すためトークン消費が増える。
- **実行時の対策**：①**プロンプトの3基本**（曖昧語を避けて具体的に書く／1プロンプト1ゴール／対象ファイル・関数を名指しする）。実行前の6要素が整っているほどプロンプトは短くて済み、逆に毎回長くなるなら環境整備不足のサインである。②前述のサブエージェントへの委任。
- **実行後の対策**：リファクタリングによる継続的な衛生管理。コードベースの劣化は自己増幅する（汚れたコードが次の生成の手本になり、劣化が加速度的に進む）ため、リファクタリングは「余裕があればやる美化活動」ではなく「次のタスクの実装完了確率を守るインフラ投資」である。

## 第4章 アウトプット制御のためのテスト駆動開発

### 速度と品質のトレードオフ
判定の担い手が人間しかいない限り、速度（レビュー待ちで頭打ち＝Human in the Loop）と品質（検証なき信頼で崩壊）はトレードオフの関係にある。この二択を壊す唯一の方法が、**判定の担い手を人間から機械（テスト）へ移すこと**である。

### テストという「正解の定義」
テストとは「こう操作したら、こうなるのが正解」を機械的に判定可能な形で書いたものであり、解釈の余地を消す。機械の判定は人間の判定（遅い・回数に限りがある・ムラがある）を裏返し、速く・何度でも・ぶれずに判定する。

### テストがAIを自走させる（速度の解決）
テストなしの指示は「準委任契約」（努力すれば完了）、テストありの指示は「請負契約」（全テスト通過まで自律的に繰り返す）に例えられる。自走が成立する3条件は、①明確なゴール定義、②自動実行環境、③エラー情報の可読性。これにより人間の役割は「実装者」から「設計者・検収者」へ移り、AIの守備範囲は書く作業（全体の2割）からデバッグ（8割）まで広がり、理論上5〜10倍の時間短縮が射程に入る。

### テストが最後の検証点になる（品質の解決）
人間の目がコード量を追えなくなった時代、CIに組み込まれたテストが品質保証の本体になる。テストは将来の変更からもコードを守る（リグレッション防止）。テストが緩めば、AI駆動開発を止める装置は他に存在しない。

### 従来のTDDからの転換
Kent BeckのTDD（Red→Green→Refactor）は本来「設計」を目的とし、小さな歩幅は人間の実装コストの高さゆえの規律だった。AI駆動開発ではサイクルを回す主体を人間からAIへ移し、目的を「AI出力への自動フィードバック」に変える。人間の実装コストが下がった以上、歩幅は最小である必要はなく、まとめて一括Greenにするのも選択肢になる。ただし「問題を小さく分割して考える」設計思考は人間側に残る。

### 何を・どう・いつテストするか
- **テスト予算の3ステップ配分**：①機械が判定できない領域（UI美観・ビジネス妥当性）は手動確認・人間レビューへ、②主要フローと重要な異常系はE2Eへ、③残りの境界値・異常系は単体・結合テストへ。
- **テストピラミッドの反転**：AI時代はE2Eのセルフヒーリング（AIが失敗ログを読んでテストを自分で修正）により運用コストが下がり、従来「頂点は少数」だったE2Eを「厚く広く」配置し、単体は精鋭化する逆台形へ再構成する。
- **単体・結合テストの役割**：境界値・異常系の高速な網羅。上級者向けにはFunctional Core / Imperative Shell（計算ロジックを純粋関数に、副作用を外側に分離する設計）で単体テストしやすいコードがそのまま良い設計になる。
- **いつ書くか**：不変なのは「正解の定義は実装から独立に人間が行うこと」と「機械の判定が人間の確認より先に走ること」の2点のみ。長期運用を見据えて設計を最優先するなら従来どおりテストを先に書く（Kent Beck自身、AIとの開発でもテストの一覧を先に作らせてから1つずつ実装させるスタイルを継続している）。速度を優先するなら実装とテストの同時生成でよく、探索フェーズなら最小実装で仕様を固めてからテストで保護する。

### 業界の実践例
Anthropicでは本番コードの約80%をClaudeが生成するに至っており、機械判定が受け入れの大部分を担うからこそ成立している。英国ASOSは仕様→テスト→コードを生成する「**TDVD（Test-Driven Vibe Development）**」という流れを確立し、OpenAIもAGENTS.mdにテストの実行方法を組み込んでいる。共通するのは、合格基準を実装前に定義し、人間の役割を設計と検収に絞り、テストを自動実行に組み込むという3点である。

### AIが生む「悪いテスト」からゴール判定を守る
AIは「テストを通すこと」自体に最適化してしまう（Goodhartの法則）。典型的な骨抜きは①意味のない通るテスト、②ダミー返却、③意図的なスキップ。対策は**WHATは人間・HOWはAI**という分業（人間が異常系を含むシナリオを自然言語で列挙→AIがコード化→人間がレビュー）と、Redフェーズの確認・ミューテーションテスト・テストコードへのAIレビューという品質担保の仕組みである。

### テストで守れる範囲と守れない範囲
テストが守るのは「pass/failの形に書ける機能の正しさ」まで。UIの美しさ・性能の体感・セキュリティの証明・ビジネス妥当性はテストの守備範囲外であり、第6章（AI相互レビュー・人間レビュー）と第8章（段階的リリース・監視）が受け持つ。

### テストはXにもなる
テストコードは「最も構造化された、最も曖昧さの少ないコンテキスト」として次の生成の手本にもなり、Y（品質検証）とX（コンテキスト供給）の両方として機能する一石二鳥の戦略である。

## 第5章 確率制御のためのLLMオーケストレーション

### 3つの前提
1. **揺れの正体**：LLMは生成モデルであり、トークンを確率的にサンプリングして自己回帰的に文章を生成する。同じ入力でも100回実行すれば100通りの出力が返るのは故障ではなく本質的な性質である（temperatureを下げても揺れは消えない）。
2. **モデルには得意不得意がある**：系統ごとに「安定型」（出力分布が狭く中央値に集中）と「探索型」（外れ値を許容）に分かれ、優劣ではなく適合の問題である。
3. **賢さは買えるが高い**：モデルのティア（等級）と thinking effort（思考トークン量）という2つのつまみで賢さを買えるが、上位ティアは1段下の2倍の料金になりやすく、投資の効きは逓減し、上げすぎるとoverthinkingで逆効果にもなる。

### 実装完了確率という指標
AIが1回の試行で要求を満たすコードを出力する確率を p として、厳密な測定ではなく経験則の翻訳（「定型処理なら90%以上」など3段階の見立て）で扱う。pを動かす変数はX・F・Yの3つであり、テストの有無はpに二重の影響を与える。

### 実装完了確率を最小のコストで上げる2つの手段
1. **確率を「数」で買う（並列実行）**：直列はp^nで確率が掛け算で減衰し、並列は1-(1-p)^nで指数的に増加する。方向は真逆。
   - **エラー防止の並列**（安定型×同一プロンプト）：正解のあるタスクへの保険。pの低い難所に効く。
   - **コンペ**（探索型×多様性）：正解のないタスク（UI/UX案出しなど）で複数モデルに競わせ、外れ値の中から人間が選ぶ。
   - **並列実行はテストがなければ成立しない**：テストが自動選別フィルターとして働いて初めて、並列は速度を生む。
2. **確率を「適材」で買う（タスク割り当て）**：タスクを分割し、正解の有無（特性の軸：安定型か探索型か）と複雑さ（投資量の軸：ティア×thinking effort）という2つの問いで、モデル設定を4象限に割り当てる。「強い頭で計画し、実務の頭で実装する」「安い頭で調査し、強い頭で決める」という2つの公式に裏づけられた分業パターンがある。この分業を実装するのがサブエージェントであり、モデルのティア・thinking effort・役割の指示・渡すコンテキストという4変数を設定できる。

### 判断の要諦
賢さをケチるかどうかはAPI料金ではなく人間の時間で判断する。安い通貨（API料金）を積んででも高い通貨（人間の時間）を支払う回数を減らすことが編成の目的である。オーケストレーションの設計はY=F（X）の好循環の入口の品質を決める。

## 第6章 最適化を壊さないAIによる相互レビュー

### 相互レビューの3条件
1. **レビューに特化した目的を持つ**（実装のついでではなく専任）
2. **定性評価である**（テストの合否＝点の判定に対し、レビューは言葉による面の評価）
3. **実装の経緯（コンテキスト）を共有しない**（自己レビューの盲点を避ける）

### なぜテストだけでは足りないか
- **単一ゴール最適化**：RLHFの学習構造上、複数の望ましさが1つの報酬（スカラー値）に畳み込まれるため、最も報酬に効く基準（テスト通過）だけが強く追われ、可読性やSSoTなど他の基準は後回しになる。
- **テストは点でしかない**：個別機能が正しくても、SSoT違反のような「操作の組み合わせで初めて現れる」矛盾はテストの合否をすり抜ける。
- **自己レビューの限界**：Degeneration of Thought（思考の退化）により、AI自身の反省だけでは新しい視点が生まれない。Multi-Agent Debateが対策として提案されている。

### 相互レビューがX・Y・Fを横断的に守る仕組み
- **Xを守る**：テストは通るが汚いコード（SSoT違反や開発ルール違反）をマージの入口で止める関所として働く。
- **Yを守る**：フィードバックの抜け漏れを拾う、偽のY（テストハーネス自体を細工した偽装）を暴く、テストに書ききれない領域を言葉で面的に補う。
- **Fを守る**：オーケストレーションの各工程間に「出す側」と「検査する側」の関所を置き、並列実行で残った複数の合格候補（テストは足切りしかできない）から最良の1つを選ぶジャッジ役を担う。

### 運用の5点
1. **観点を言語化する**（判定可能な粒度でルールファイルに書く）
2. **優先度を3段階で定義する**（PO：必須修正・マージ不可／P1：原則修正／P2：改善提案）
3. **テストコードそのものをレビューする**（「実装とテストの結託」を崩す）
4. **フィードバック振動を止める**（合格の閾値・Good Enough基準・ラウンド数上限という3つの終わりの条件）
5. **人間との境界を引く**（影響範囲とビジネス文脈の必要性で判断。3社の公式見解も、AIはマージをブロックせず最終判断は人間に残す設計で一致する）

適用場面はプルリクエストのレビュー、実装前の設計ドキュメントのレビュー（欠陥は下流ほど修正コストが高くつくため、上流での指摘が効果大）、セキュリティ専門エージェントなど観点特化のレビューに広がる。

## 第7章 AI駆動開発を成立させる実践フロー

理論を「毎回自動で効く装置」としてリポジトリに固定し、その上で8ステップの開発フローを回す。

### 第1幕：3つの装置
**X装置（リポジトリ設計）**
- すべての前提はGit管理（AIの失敗を「巻き戻せる失敗」に変える安全網。お試しブランチで大胆な変更も試せる）
- エージェント向けREADME（AGENTS.md / CLAUDE.md）：詳細を抱えず「地図（索引）」に徹する
- コードのファイル構造：①1ファイル1責務、②機能単位でトップレベルを区切るフォルダ構成
- クリーンアーキテクチャの是非：機能ごとの大きなフォルダ分けは必須、その先の層分割は規模と好みで判断可（採用するならリンター＋CIで機械的に強制する）
- ルールファイル：1ファイル1トピックで分割し、pathsで対象を限定。機械的に検証可能な文で、やってはいけないことを名指しで書く
- スキル：「こうやるとうまくいく」ノウハウ。description（何をするか・いつ使うか）が呼び出しの命
- 要件定義ファイル：目的・対象ユーザー・ゴールを1枚に。要件（何を・なぜ）→設計（どう）→タスク（どの順に）の3段階（spec-kit / Kiroの型）
- 外部情報の接続：ログ基盤（Sentry等）、データベース（読み取り専用接続や環境分離で安全に）、デプロイ環境（Vercel等）へのMCP/CLI接続。認証情報は「Gitに入れない・チャットに貼らない」
- エラーをAIが読める形にしておく：構造化エラーログ（関数名・入力・エラー内容を添える）

**Y装置（テスト実装）**
- テストが1コマンドで走る土台（Vitest / Playwrightなど標準ランナー）
- 並列実行に耐えるテストデータ（テストごとに専用データを作って消す設計）
- 無効なテストをルールとレビューで弾く2段構え（禁止事項の明文化＋レビューでの検出）

**F装置（並列実行環境）**
- ローカル並列（Git Worktree）：ブランチごとに独立した作業ディレクトリでAIを並走させる
- クラウド並列（タスクを投げてPRで受け取る）：サンドボックス環境で自走・完成をPRで受け取る
- サブエージェント定義ファイル：モデルのティア・thinking effort・役割・渡すコンテキストの4変数を1枚に固定し、観点別レビューや別系統モデル（Claude Code⇄Codex）の呼び出しに活用する

### 第2幕：開発フローの8ステップ
2つの介入点（実装前のプランドキュメント／実装後のテスト駆動リファクタリング）を軸に、以下の流れで回す（目安時間：Step1が60分と最長で「山1」、Step4〜6の実装→テスト→レビューの反復が「山2」）。

**プランドキュメントの作り方**：人間が一気に書き上げるのではなく、短い依頼から始めてAIに**逆質問**させ（「認可は既存の仕組みを共有しますか、専用にしますか」等）、技術面・エッジケース・トレードオフを聞き尽くしてから1枚の文書に落とす（Anthropic推奨のインタビュー方式）。仕様（概要・背景・スコープ外）→実装（詳細設計）→テスト計画（影響範囲・新規ケース・実装順・コミット前テスト）の順で埋める。外部接続（例：会議の文字起こしツールtl;dvへの接続でクライアントの発言を一次情報として取り込む）も材料になる。プランドキュメントはX・Y・Fの3変数を同時に底上げする横断レバーであり、実装順にはどのタスクをどのAIに割り振るかという第5章のオーケストレーションの采配まで書き込む。

1. プランドキュメントの作成（概要・背景・詳細設計・テスト影響範囲・新規テストケース・実装順・コミット前テスト実行・スコープ外の8項目）
2. プランのAI相互レビュー（設計整合性・セキュリティ・運用・ビジネス整合性）
3. プランのAI相互レビュー（テストの網羅性。異常系・境界値の穴を人間とAIで一緒に探す）
4. 実装（LLMオーケストレーションの主戦場。強い頭で計画→実務の頭で実装、あるいは並列コンペなど）
5. テストの実装と全通過の確認
6. 実装のAI相互レビュー（プランとの乖離・エラー候補・設計のきれいさ）
7. 人間のレビュー（設計判断とビジネス整合に集中）
8. テスト駆動リファクタリング（定期的な工程として固定し、劣化を打ち消す）

### 第3幕：現場で実際に起きたこと（実体験5つ）
1. **Xを本番の運用基盤まで広げたら障害が減った**：デプロイ設定やログをXに取り込むまで「コードは完璧なのに動かない」障害に悩まされた。
2. **テストの網羅をAIに任せて後悔した**：ビジネス文脈の判断は人間にしかできず、AI任せの一覧はE2Eの網羅が薄かった。
3. **AIが書いたテストに騙された**：意図的なスキップやダミー返却の「骨抜き」に本番で気づいた経験から、ルール＋レビューの2段構えが生まれた。
4. **レビューのしすぎはかえって毒になる**：指摘ゼロまで往復させると過剰品質・コンテキスト肥大を招くため、往復には上限（1〜4回）を設けている。
5. **リファクタリングを後回しにして無限ループに捕まった**：実装完了確率が体感50%を切るまで悪化したが、週1回・夜間のテスト駆動リファクタリングを3週間続けて回復した。詰まったときは**X→Y→Fの順に疑う**のが原則（並列でごり押しするのは最後の妥協策）。

## 第8章 AI駆動開発を組織へ展開するために

### 個人から組織への3つの壁
個人の実践は個人の裁量という見えない統制に支えられている。組織ではこれが崩れる。
1. **開発のやり方の壁**（属人性、単一障害点）
2. **品質の責任の壁**（責任の所在が組織に移る）
3. **障害の影響の壁**（規模が大きく復旧・影響範囲の設計が必要）

（実例：2017年メルカリのCDN切り替え事故。原因はコードのバグではなくインフラ構成の不整合であり、単体テスト・E2E・コードレビューのいずれでも検出できなかった。Y=F（X）の射程外のリスクが存在することを示す。）

### ガバナンスの3段階
1. **開発段階**（Y=F（X）の式の中：XとYを組織の仕組みで固める）
   - 組織で統制するXのルール：全社共通ルール（モデル認可リスト・実行権限の最小化・認証情報の隔離）＋チーム別ルールの2層構造。Managed Settingsのような強制配布の仕組みで個人の裁量を上書きする。
   - Xのハーネス環境の共有資産化：シニアの暗黙知をルールとして明文化し、経験レベルに依存しない品質を実現する。
   - AIに見せるX／見せないXの設計：IaC（Infrastructure as Code）でコードの外の設定をコードに引き込み、本番DBなど見せてはいけないものは接続自体を断つ。
   - Yの統制（3層レビュー体制）：テスト（全コード・自動）→AIレビュー（全PR）→人間レビュー（重要箇所のみ）と対象範囲を絞りながら判断密度を上げる。コアと非コア機能を区分し、リスクに応じて濃淡を調整する。
2. **リリース段階**（式の射程外を出し方で吸収）
   - フィーチャーフラグ（機能単位のON/OFF、問題発生時に即座に無効化）
   - カナリアリリース（バージョン単位で5%→25%→50%→100%と段階的に展開）
   - ただしセキュリティ事故・情報漏洩はロールバックで被害を巻き戻せない点に注意
3. **運用段階**（本番稼働後の監視）
   - SLI/SLOと可観測性（機能的品質の測定）
   - LLMによる異常検知（LLM-as-a-Judgeパターンの運用応用。テレメトリ×判定基準→判定LLM→アラート。ただし致命的な安全条件は固定ルールで強制し、LLMは「未知の未知」の発見に使う）

### 段階的導入とリーダーシップ
- AI駆動開発の導入は技術の導入ではなく**組織変革**であり、心理的抵抗を伴う。
- **AI Enablementチーム**による伴走型支援（パイロットチームへの常駐、ルールのカスタマイズ、成功事例の横展開、つまずきの早期発見）を推奨し、最終ゴールは自走できる状態を作って自らを不要にすることである。
- 組織はトップダウンで動く。アッパーマネジメントを味方につけ、経営層は投資対効果（開発者数×削減時間×人件費 対 ツール費用）で動かす。
- KPIは判断を支えるデータであり、導入を推進する力そのものではない。**原動力は「やると決めて実行する」リーダーの意志**である。

### A.1.2 ルールファイル（1）アーキテクチャ

> 1ファイル1責務・どこに何があるかわかる構成・機能境界・副作用の分離（Functional Core / Imperative Shell）を固定したルール。

```yaml
paths:
  - "src/**"
```

```markdown
# architecture

## 構造（どこに何を置くか）
src/features/<機能名>/  # ロジックの本体。機能単位で区切る
  <機能名>.controller.ts  # リクエストの受け口。ロジックを書かない
  <機能名>.service.ts     # ビジネスロジック
  <機能名>.repository.ts  # データベースの読み書き
  <機能名>.types.ts       # 型定義
src/lib/               # 機能横断の共通処理のみ

迷ったらこの順で問う：
1. 特定機能の業務ロジック → `features/<機能名>/`
2. どの機能にも属さない基盤 → `lib/`
3. 複数機能で共有したい処理 → 安易に共通化せず、まず各機能に置く

## 1ファイル1責務
- ファイルの担当を一文で言えること。「請求書の金額計算」は合格、「請求書まわりの処理いろいろ」は失格
- ファイルが肥大したら、責務の境界で割る

## 機能境界
- 他機能のテーブルへ直接クエリしない。所有機能の service 関数を経由する
- controller に業務ロジック・クエリを直書きしない。service の関数を呼ぶだけにする
- barrel export（index.ts への集約・再エクスポート）禁止。実ファイルへ直接 import する

## 副作用の分離（Functional Core / Imperative Shell）
- 業務判断・計算・変換は純粋関数に集める（Functional Core）
- DB の読み書き・外部 API・時刻・乱数・環境変数参照は外側の薄い層へ寄せ、Core が返した結果を実行するだけに近づける（Imperative Shell）
- 狙いは、複雑なロジックを外部依存なしでテストできる形に保つこと
```

### A.1.3 ルールファイル（2）テスト

```yaml
paths:
  - "tests/**"
  - "e2e/**"
  - "vitest.config*"
  - "playwright.config.*"
```

```markdown
# testing

## 種別と実行コマンド
| 種別 | ツール | 置き場所 | 実行 | 何を守るか |
|------|--------|----------|------|-----------|
| 単体 | Vitest | `tests/unit/`（srcの構造を再現） | `npx vitest run` | ロジックの境界値・異常系 |
| E2E | Playwright | `tests/e2e/` | `npx playwright test` | 主要フロー・認可・状態遷移 |

- 単体の置き場所は src のパスを再現する（例：`src/lib/tax.ts` → `tests/unit/lib/tax.test.ts`）
- E2E は実行前にシードデータの投入とアプリ起動が要る

## 単体と E2E の切り分け
E2E で検証する：
- ユーザーフローの完走（ログイン→操作→結果の確認）
- 認証・認可（他人のデータが見えない・権限で表示が変わる）
- 複数画面や API をまたぐ統合動作、状態遷移（ローディング→成功／エラー）
- 実 API との通信を含むフロー（モックしない）

単体で検証する：
- 純粋な計算・整形・バリデーション（外部 I/O なし）
- E2E では網羅しにくい細かい分岐

## E2E のシードデータ
- シードは1つの定義ファイルに集約し、テスト内で独自のマジック値を作らない
- 最低限用意する：プラン／ロール別のログインユーザー（管理者・一般など固定メール＋固定ID）、権限確認用の「別の組織のデータ」
- 実行の流れ：`npm run db:seed`（シード投入）→ アプリ起動 → `npx playwright test`
- 変更を伴うテストは専用データを fixtures で作り、後始末する

## 骨抜き禁止
```js
// ✕ 何も守っていない
expect(result).toBeDefined();

// ✕ 常時成功モック（本物が壊れても通る）
vi.mock('./calcTax', () => ({ calcTax: () => 1000 }));

// ✕ 条件付きスキップ（環境がないと黙って成功扱い）
if (!process.env.API_KEY) return;

// ○ 期待値を固定して assert する。境界の両側を書く
expect(calcTax(10000)).toBe(1000);
expect(calcTax(0)).toBe(0);
```
- E2E でアプリ内部の API 応答をモックしない
- `.only` / `.skip` を残したままコミットしない
- 新規テストは先に Red（失敗）を確認してから実装する

## テストの独立性（並列実行対応）

**① tdd**（テスト駆動開発の実行手順）

```yaml
name: tdd
description: テスト駆動開発で機能追加・バグ修正を実装する。テストリストから1件ずつ Red、最小の Green、Refactor を回す。

```markdown
## 0. 開始条件
- ルールファイル（testing.md と変更パスに該当するもの）を読む
- 期待する振る舞いは要件・プランを出典にする。実装コードを正解にしない
- 期待結果が曖昧、仕様と実装が矛盾する場合は、推測でテストを書かず停止して報告する

## 1. テストリストを作る
変更後に観測できる振る舞いを列挙する（正常系・境界値の両側・異常系・既存挙動での回帰）。
全件のテストコードを先に書かない。最も小さく設計を前進させる1件だけを選ぶ。

## 2. Red（失敗を実測する）
選んだ1件のテストを書き、対象テストだけを実行して失敗を確認する。
未実装の振る舞いが原因で失敗する状態にする（コンパイルエラーは Red ではない）。
最初から通ってしまったら、実装済みか、assert が弱いかを判定する。

その1件を通すのに必要な実装だけを書く。固定値の返却・テスト専用分岐・assert 削除・skip は「最小実装」ではない。
同じ失敗を2回繰り返したら、試行を増やさず前提と設計を見直す。

## 4. Refactor（Green を保って整理）
すべて Green の状態でのみ行い、変更のたびにテストを実行する。

## 5. リストが空になるまで繰り返す
作業中に見つけたシナリオはリストへ追加する。完了時は、テストリストの全項目と実装されたテストを対応づけて報告する。テスト通過だけを完了証明にしない。

## A.3 プランドキュメントの完全版

第7章 Step 1の8項目を「請求書のアップロードと OCR 読み取り」で全部埋めた実物。未確定の論点は【要確認】をつけて残す。プランは完成品ではなく、Step 2の AI レビューと Step 3の人間の承認で磨かれる叩き台である。

```markdown
# プラン：請求書のアップロードと OCR 読み取り
状態：レビュー中｜元資料：docs/requirements/invoice-ocr.md（要件定義）

## 1. 概要
請求書の PDF・JPEG をアップロードすると、OCR で金額・取引先・日付を抽出し、仕訳の下書きとして表示する。読み取れなかった項目は空欄＋要確認マークで示し、人間が確定するまで仕訳には反映しない。

## 2. 背景
要件定義のストーリー1（P1）に対応する。経理担当者の転記作業が月約20時間あり、その大半が「PDF を開いて金額と取引先を打ち直す」作業のため、読み取りの自動化で仕訳開始までの時間を削る。FR-001〜003・SC-001 が受け入れの基準。

## 3. 詳細設計
変更するファイル：
- `src/features/invoice/invoice.controller.ts` — アップロード受け口。`POST /invoices/upload` を追加（multipart、PDF/JPEG のみ受理、10MB 上限）
- `src/features/invoice/ocr.service.ts` — 新規。OCR API の呼び出しと結果の正規化（金額：整数円、日付：ISO 8601、取引先：文字列）
- `src/features/invoice/draft.service.ts` — 新規。下書き仕訳の作成。読み取れなかった項目は null で保存し、needs_review フラグを立てる
- `src/features/invoice/invoice.repository.ts` — `invoice_drafts` テーブルの読み書きを追加
- `prisma/schema.prisma` — `invoice_drafts` テーブルを追加（id, file_url, amount, vendor, issued_on, needs_review, status, created_at）

判断済みの論点：
- OCR は外部 API（クラウド OCR）を使い、自前実装しない。API キーは環境変数
- 認可は既存の `requireMember()` を流用し、この機能専用の仕組みは作らない
- 元ファイルはオブジェクトストレージに保存し、DB には URL だけ持つ
- 【要確認】OCR API の月額上限。超過時に読み取りを止めるか、課金を許容するか

## 4. テスト影響範囲
- 既存の請求書一覧 E2E（invoice-list.spec.ts）：下書きステータスの表示が増えるため、一覧の件数アサーションを更新する
- それ以外の既存テストへの影響はない（新規テーブル・新規エンドポイントのため）

## 5. 新規テストケース
単体（Vitest）：
- 金額の正規化：「1,234円」「¥1234」「1234.00」→ 1234。不正文字列 → null
- 日付の正規化：「2026/7/1」「令和8年7月1日」→ "2026-07-01"。不正 → null
- 下書き作成：3項目すべて読めた場合 needs_review=false、1つでも null なら needs_review=true

E2E（Playwright）：
- 請求書 PDF をアップロード → 下書きに金額・取引先・日付が表示される（シナリオ1）
- 読み取れない項目のある PDF → 該当項目が空欄＋要確認マーク（シナリオ2）
- JPEG 以外の画像（PNG）→ 受け付けずエラー表示（FR-001 の裏）
- 下書きのまま → 仕訳一覧に現れない（FR-002）

## 6. 実装順
1. スキーマ追加と repository（安価なモデルのサブエージェントに委任）
2. 正規化の純粋関数（金額・日付）：失敗するテスト → 最小実装（同上）
3. ocr.service.ts：OCR API 呼び出し。テストは API をモックした結合テスト（中核ロジックのため上位モデルで実装）
4. draft.service.ts と controller：失敗する E2E → 実装（上位モデル）
5. 実装完了後、観点別レビュー3体（セキュリティ・テスト網羅・設計整合）を並列で走らせ、P0/P1 を修正
